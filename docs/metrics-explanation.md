# 大白话：为什么请求成功数不能当成游戏成功数

一个玩家点一次提问，断网后可能重试三次。如果把三个请求算成三个问题，访问量看起来漂亮，游戏账却错了。所以几本账分开算。

```text
会话表       → 什么时候开了一局
轮次表       → 哪些问题真正成功且计次
HTTP审计     → 尝试了几回，包括失败和重试
反馈/任务表  → 什么时候提交反馈、建立修复任务
审核发布审计 → 什么时候批准、驳回或发布
                 ↓ 同一数据库读快照
            私有汇总 + 公开来源分组
                 ↓ 独立管理员手动点击
           查看一页 / 另读一次完整导出
```

“成功计次”只说明系统完成应计次的轮次，不说明AI答对。正确与否仍需独立题集、可靠标签和真实评测，不能由HTTP200或格式合法推出来。

## 测试数据不能假扮真实用户

新的临时库确实放了200局、1000轮、5000审计。其中real标签只验证“遇到这个标签如何统计”，不是变出真人。测量一直标成合成数据；真实站点人数、满意度、模型质量仍没有由它证明。

测试、合成、历史、来源不明各单列。旧库没存的审计不补造。版本不明就显示未知，不填今天的版本，否则解释不了当时哪套规则出问题。

## 统计也需要对得上账

汇总读到50任务，分组却读到刚新增的第51个，会矛盾。一笔读快照让两部分看到同一时刻。包含校验最多3秒，页面只手动查，不在玩家提问时后台轮询。

取舍：跨页是不同快照，新数据可能改变总数。完整文件用另一次完整导出，不拼多页。过大就拒绝并缩范围，不悄悄删后半份还叫完整。

## 发布率不是正确率

本周新建10修复任务，现在3个发布，就是3/10。其余7个未结束也不能从分母消失。没任务时是null，不写100%。它描述流程进展，不描述修对与否，也不是截止某天的历史状态回放。

索引像按时间编的目录，帮助数据库找范围。不是保证每次更快：这次小规模实测前后差异很小，来源核对和JSON聚合仍占时间。不能包装成巨大加速或上线容量承诺。

发布前“候选方案测试通过”像检查新零件，不能代替发布后“装到这套规则上再次检查”。D18本地已增加单独的管理员检查入口，记录实际发布版本与当时题集；检查计划先落账，成功、发现反例、检查不完整、还没完成分别保留。超时没做完的题不能从分母消失，旧失败也不能在重试时被覆盖成成功。固定检查不调用真人使用的模型，所以遇到它判不了的正常问法会写“不支持检查”，不会把游戏问法判成异常；玩家正常游戏也不会自动多做这套检查。

管理页把测试流量与真实流量分开。没有真实检查时，可以说明“目前尚无真实观测”，不能说明“没有出过错”。005以前或证据损坏时直接显示未知；覆盖开始前的窗口显示覆盖不完整。不自动重建过去的记录，也不等于已经上线。实现与当前门禁见[D18 ledger](superpowers/plans/2026-10-13-d18-progress.md)。
