# 为什么 AI 建议不能直接上线

AI 可以建议把“不是”改成“是”，但它也可能理解错故事。自动测试能发现一些问题，却不能证明一句话在所有语境中都正确。所以这里让 AI 做调查和提案，让人决定是否接受，再把“接受”与“真正发布”分开。

## 先看证据，再做决定

```text
玩家的真实回答反馈
    → 人工审核反馈 + 单独检查隐私
    → 明确启动有预算的 Agent
    → 调查/机械回归/保存未批准候选
    → 人工看完整问题、事实、限定条件、旧新规则和报告
    → 单独批准
    → 单独发布
    → 新局生效；必要时回滚，历史仍在
```

玩家说“应该答是”只是玩家的判断。模型说“根据事实应该答是”也只是模型建议。页面另外展示实际故事事实和限定条件，避免只看一段听起来很有道理的摘要。管理员必须明确确认“答案有完整事实支持”和“不依赖当前玩家上下文”，再写理由；绿色测试报告不会自动帮人勾选。

还要看玩家当时到底在聊什么。比如同样的“他死了吗？”，“他”可能指小明，也可能指小王。页面把真实的原问题和之前对话放在脱敏后的模型输入旁边，让人能核对区别；玩家自己填的“反馈背景”不冒充原对话。额外原文只给管理员看，不自动多发给修复模型。原对话缺失或太大就明确说无法完整核对，不偷偷删几句后假装可以批准。

格式错误和意思错误也不同。返回奇怪字段、超预算动作可以用程序识别。正常格式里的“是”，如果意思错了，仍要靠真实独立案例和人工事实核对。这套流程没有宣称能自动识别所有语义错答，也不靠新增付费模型裁判。

## 为什么批准和发布分两步

批准相当于签字认可一份具体提案，发布相当于把这份提案投入使用。签字之后，不能把答案或引用偷偷换掉再沿用签字。服务器因此同时检查候选、报告、来源、版本以及实际批准操作的绑定。

如果两个管理员同时发布，不能让后来的操作悄悄覆盖先前更新。版本号检查相当于问“你确认时看到的还是现在这一版吗？”已经变化就拒绝，并要求重新核对，而不是自动替人作新决定。

这增加了一次明确点击和版本冲突处理；换来的是不会因为测试变绿或重复网络请求就自动更新游戏。

## 已经提交，但没收到回复怎么办

断网发生时，服务器可能已经保存了批准或发布。页面不能直接说“失败，所以什么都没发生”，也不能换一个请求编号自动再发布。

它保存原操作内容，只允许手动核对，或用原编号和原内容重试。服务器返回原操作凭证，不重复执行。当前实际状态仍要刷新读取，旧凭证不能恢复已撤销的权限。

保存前还要再检查一遍依据。例如刚核对完题集，管理员就撤回了它，不能沿用刚才的检查结果把改动保存上线。新批准/发布会在最终保存处复查；发现变化，提案状态、发布版本和相关记录一起撤销，不留下“发布了一半”。这项检查不加到玩家每次提问里。

## 回滚不是删掉后来发生的事

回滚把“新游戏应使用哪版规则”指回已验证的历史版本，同时留下新的操作记录。不删除候选、不删除发布历史，也不用老备份覆盖后来新增的反馈和游戏。

已经开始的游戏保留原固定版本，避免玩家玩到一半答案突然变化。新开游戏按当前指针开始。若某版必须禁止继续使用，需要另走已有的明确暂停机制。

## 零成本下能证明什么

隔离测试使用声明为合成的故事、独立冻结的合成案例、固定测试模型和真实数据库/浏览器流程。它能证明权限、事务、预算、重试、页面和回滚等工程行为。

它不能证明真实免费模型有多准确、真人审核有多可靠、真实用户喜欢改进后的体验，或生产部署已经安全。真实案例仍需独立人工审核，供应商免费资格仍需按实际账户核实。本轮没有调用付费模型或自动部署生产。

面试时可以说“我构建了受控反馈修复闭环，并用真实事务和浏览器验证了发布安全边界”，不能把合成回归通过率说成真实模型准确率。当前证据及待定部分见 [TS15 状态](ts15-status.md)，字段和限制见 [接口参考](candidate-review-reference.md)。
