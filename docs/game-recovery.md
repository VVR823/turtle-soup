# 为什么断网后要同步原请求

玩家按下“发送”，不等于服务器一定没收到；网页报错，也不等于服务器没扣次数。服务器可能已经保存了一问一答，只是回复在回程中丢了。详情见 [测试运行时参考](test-runtime.md)；本地复现见 [测试指南](testing.md)。

## 一个操作的恢复过程

```text
浏览器保存请求编号和原问题
           ↓
发送给服务器 → 原子保存一轮问答和计数
           ↓                  ↓
收到回复                   回程断网
           ↓                  ↓
读服务器对局         刷新后查询原编号
           └─────────┬────────┘
                 展示已保存状态
```

保存编号失败时不发请求。刷新后先查原编号；只有服务器说这一轮不存在，并确认原对局仍可玩时，才携带同一个编号、同一个问题重发。不偷偷换一个编号，否则服务器会把它当成新问题。

服务器的一轮问答也有明确状态：

```text
同一请求编号 + 同一问题 → 查已有记录并重放
新请求 → reserved（预留，未扣数）
             ├─ 正常完成 → completed（问答、次数、响应、审计一起提交）
             ├─ 技术失败 → failed（零扣数，保存失败响应）
             └─ 业务租约过期 → expired（零扣数，旧执行者不能迟到覆盖）
```

免费提醒也可以是 `completed`，状态本身不决定扣数；服务器按结构化结果决定。`reserved` 查询返回处理中，不启动第二次模型调用。业务租约过期也不表示仍阻塞的模型线程已经退出；只有实际完成清理，模型名额才释放。对应事务、迟到与重放的断言见[游戏恢复证据](acceptance-a13-a17.md)。

如果服务器明确给出已失败的业务结果，再读取确认后的对局，页面才可以说“没有扣次数”。普通断网、429、503、无法识别的回复都不能推出这句话。操作记录保留，玩家可以稍后点击“同步原对局”。仍在处理的请求最多查询三次，间隔至少一秒；限流回复会停止自动查询，保留原编号，等待提示时间后手动同步。

## 切换页面后，旧回复不再管新页面

每次页面初始化都有一个新的执行代号。切换汤品或难度时，旧执行代号失效、网络请求取消。即使底层请求仍晚到，旧代码也不能更改新页面、保存指针或待恢复编号。

先玩A、去B、回A时，A按路由保存的原请求仍可查。只有服务器核验它属于A，查询期间没有别的页面改记录/指针时，才接回A，不是旧回复抢占新页面。次数字段缺失不能冒充无限，只有显式null是合法无限模式。

React 开发模式会进行额外的初始化/清理检查。这里会接回已经保存的开局编号，测试验证同一个控制器再次启用仍能工作。这是单元/组件证据，不把生产浏览器构建冒充开发模式 StrictMode 双执行实测。

## 已揭晓结果也是原对局的一部分

揭晓按对局幂等保存。回复丢失后先读取对局；服务器已有最终结果就直接显示，不再猜分数。刷新、回大厅不会清除恢复指针。旧分数继续标为旧口径，新结果区分已确认事实覆盖与剧情进度；“还原程度”仍显示尚未独立评估。

若原问题查不到，但同一局已在另一个页面结束，显示核验后的结束结果，不补发问题、不凭404承诺未扣数。

另开一局是显式操作。若上次请求尚不确定，需要玩家确认放弃它的浏览器恢复入口，但不会删除服务器历史。旧指针在新局核验成功前保留。

## 代价与边界

确认一问后多读一次原对局，增加一个普通 HTTP 往返，不额外调用模型。存储损坏、结果未知时会暂时阻止新操作，避免重复扣次数或覆盖旧记录。只有合法、可核验的服务器状态才更新页面；不是“问题语义难判”就报异常。

跨标签页采用记录/指针归属检查，不是全浏览器原子锁，也不保证两台设备自动共享恢复状态。浏览器数据被用户清空、隐私模式存储失败、Safari 真机键盘与生产网络都需要各自验证。合成 FakeModel 测试证明工程流程，不能证明模型语义准确率。
