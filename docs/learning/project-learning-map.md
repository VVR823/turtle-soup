## 第一站：一次提问究竟经过哪里

从前端 `src/lib/game-controller.ts`、`game-journal.ts` 看起。前者负责当前页面状态，后者在发送前记住这次请求的编号和内容。后端入口在 `backend/app/main.py` 的 `chat`，不是一个尚不存在的 `routers/chat.py`。

之后读 `backend/app/game_service.py` 的 `ask`：先为这轮问题登记一个位置，再在数据库事务外调用主持逻辑，最后交给 `game_store.finish_turn` 一次保存结果。主持判断在 `ai_host.handle_host_response`；数据事务和恢复在 `game_store.py`；答案的严格格式在 `schemas.py`。`db.py` 保留兼容入口，不应把所有业务继续塞到它里面。

最小关系：页面保存请求编号 → 后端登记问题 → 规则或模型给出结果 → 一次保存消息和计数 → 页面收到结果或按原编号恢复。

能独立回答这三个问题，再往下读：前端为什么先保存编号？为什么等模型时不一直锁住数据库？模型已经答完但页面没收到时，怎样知道该不该再扣一次？

## 学习卡 1：断网后不能重复扣次数

业务问题：服务端已经保存答案，手机刚好断网，玩家点击重试。如果当成新问题，可能又调模型、又扣次数。

入口：`main.chat` → `game_service.ask` → `game_store.reserve_turn/finish_turn`；页面恢复读 `game-controller.ts`。

设计原因：每次真正的新提问有唯一 requestId。同编号、同内容取回原结果；同编号换内容会冲突。相同文字使用新编号才表示玩家主动再问一次。所谓“幂等”，在这里就是重复送来同一件事，也不会做第二遍。

失败案例：已保存结果的响应丢失。保护目标是返回原答案和原计数，不再次调用模型；失败结果也不能被重试偷偷重新执行。

验证：已有 `backend/tests/test_game_request_recovery.py` 使用真实本地HTTP、临时库和注入模型检查成功/失败的重复提交、次数和调用量，不连接真实免费模型。学习时可在仓库根目录单跑：

```powershell
node scripts/test-backend.mjs backend/tests/test_game_request_recovery.py -q
```

自测：去掉“按 requestId 查旧结果”会发生什么？如果断网发生在保存之后，还能把这轮算作完全没发生吗？不要只回答“加锁就好了”。

## 学习卡 2：合法格式不等于答案正确

业务问题：模型可能回答一大段无关文字，也可能规规矩矩地给出“是”，但事实上应当回答“不是”。这是两种不同的问题。

入口：`schemas.HostResult`、`model_gateway.py`、`ai_host.py`；事实依据见 `host_evidence.py`，安全规则见 `host_rules.py`。

设计原因：程序只接受约定的五类判断及合理的结果组合，不能从随意文本里硬找一个“是”就当合法。收费、规则来源、版本、剩余次数由程序决定，不由模型自报。格式正确却语义答错，不能单凭格式校验自动识别，需要事实、已知反例和人审等额外证据。

失败案例：模型输出非法文本。该次作为系统失败，不扣次数；但它依然可能消耗一次模型请求。另一面：模型输出合法但错误的“是”，不能谎称格式校验已经证明它正确。

验证：现有 `test_host_contract.py`、`test_model_gateway.py`、`test_turn_failure_recovery.py` 分别覆盖格式、调用故障、失败与计数保护。当前正常问法也有既有回归，不靠把所有问题判异常来提高安全性。

```powershell
node scripts/test-backend.mjs backend/tests/test_host_contract.py backend/tests/test_turn_failure_recovery.py -q
```

自测：游戏次数、模型请求次数、模型实际消耗的token为什么不是同一个东西？“格式合法”和“有证据支持”为什么不能混为一谈？

## 学习卡 3：评测不能只算答成功的题

业务问题：计划测试8题，2题接口失败。如果只算成功返回的6题，数字会变得好看，但用户遇到的失败被藏起来了。

入口：`backend/eval/runner.py`、`run_contracts.py`、`metrics.py`、`comparison.py`、`run_cli.py`，使用说明见[评测运行器](../evaluation-runner.md)。

设计原因：每个计划问题都留一行：正确、错答、提醒、非法输出、接口失败、未尝试，都不能悄悄删掉。正式标准答案只用于算分，不能先喂给被测试模型，更不能把它塞进对话历史替模型纠错。重复实验保留好的和坏的每次结果。

失败案例：测试中的8条合成记录，3条正确、2条系统错误。总准确率是3/8，不是3/6。这个数字来自机械测试夹具，不是网站真实模型的准确率。缺少token用量应写未知，不填0。

验证：现有 `backend/eval/tests/test_runner_accounting.py` 写明手算的完整矩阵和分母；它与运行器、上下文和CLI的测试分层。TS12已完成本地独立审查修复；Fake运行器测试不能替代人工标签和真实模型比较。

```powershell
node scripts/test-backend.mjs backend/eval/tests/test_runner_accounting.py -q
```

自测：如果每个汤的测试题数不同，直接平均各汤准确率和按所有题算准确率有什么区别？“同预算”为什么还要说明重试、时间和上下文限制？

真正学会的标准：能复现一个失败案例，指出修复位置，解释为何要这样改，并运行对应测试。AI生成过代码不妨碍你掌握它；但能讲一遍设计还不等于所有代码、运维和实验都由你独立完成。面试最好如实说“AI辅助，我负责需求、验收和这些我能证明掌握的技术部分”。
